## Findings, ranked by comparison relevance

1. **P2: `post_velocity_unsupported` cannot detect an incorrect velocity direction.** `tools/momentum-tape.py:523` reduces post velocity to horizontal magnitude; `:535–537` compares scalar magnitudes. A disposable subclass saves the real resolved velocity, negates its horizontal components after movement, then restores the saved vector before the next step. This isolates the telemetry fault while preserving the real trajectory. On the actual step fixture, control and injection have identical positions, yaw, input, settings and timing for all 320 ticks, while their post velocities differ by up to **18 m/s**. Both integrity reports are clear. The reduced 40-tick flat replay reproduces twice: at tick 20, displacement is `[0, approximately 0, -5.250091]` m/s while post velocity is `[0, 0, +5.25]`; 39 ticks exceed the existing tolerance when applied to the vector error, but no integrity flag appears.

   Repro: run `reverse-min-1/evaluator/plan.json` with `--world fixture:flat --motor-script "$E/variants/reverse-vector-injection.gd" --headless --sensitivity 1 --timing fixed --render-fps 30`, using the copied wrapper and a fresh `--out`. Repeat is `reverse-min-2/`; the longer control comparison is `direction-comparison.json`. Direct fault: the flag verifies horizontal speed consistency only. Possible effect: a heading/projection error could receive a clean integrity report. Add a separately defined vector check, or name and document this check as magnitude-only. The vector comparison would need explicit treatment of legitimate collision/slope transitions; the probe does not establish that every real velocity/displacement vector difference is a motor fault.

2. **P2: an acknowledged reset is still counted as travel and peak speed.** `evaluate()` identifies respawn discontinuities and excludes them from mismatch windows, but `tools/momentum-tape.py:585` aggregates every displacement into `outcome`. A fixture game calls the existing `reset_to()` and increments `respawn_count` between the early/late samples. The one-tick, no-input repro marks `discontinuities: [0]`, yet reports **49.999996 m travel and 5999.999512 m/s peak displacement speed**. Travel outside that reset is exactly zero. Both repetitions agree; the original 24-tick cases agree too.

   Repro: run `reset-min-1/evaluator/plan.json` with `--game-script "$E/variants/reset-min-game.gd" --game-class '' --headless --sensitivity 1 --timing fixed --render-fps 30`, fresh output. Evidence: `reset-min-1/`, `reset-min-2/`, `finding-measurements.json`. This contradicts TAPE.md's “discontinuities rather than travel” statement. Exclude identified discontinuities from movement totals and maxima while retaining their raw samples. The fault can inflate comparison summaries; it did not produce an integrity or movement flag in this short reset case.

3. **P2: engine-spawn exceptions bypass cleanup and lose the run record.** At `tools/momentum-tape.py:299`, engine `Popen` is outside the cleanup `try/finally`, after Xvfb starts and signal handlers change. Pointing `GODOT` at an existing, hashed but non-executable test file raises `PermissionError`. In two one-tick attempts, the wrapper leaves its own **Xvfb :158 and socket alive**, with neither `run.json` nor `cleanup.json`. The reviewer explicitly terminated and reaped only those newly created Xvfb children after recording the fault; :158 is clear.

   Exact guarded reproducer: `startup-failure.py`; results: `startup-failure-results.json` and each `startup-failure-*/observed-launch-failure.json`. Use fresh output names when repeating. This is an injected OS launch failure, not a Godot crash. Put resource acquisition and launch inside cleanup coverage and retain failed-launch provenance. Repeated failures can strand private displays; successful-run cleanup does not cover this path.

Both counted probes verify 24/24 counter deltas and matching motor entry/exit positions against the early/late samples. Removing only the counter retains a clean order result labelled `state_or_priority_consistency_only`, with zero counter-verified ticks. This does not re-prove the already reviewed stationary skip/double controls.

Movies differ as expected from their render timing. Evidence is each run's `motor-read-check.json` and `input-comparisons.json`.
- **Real contact versus false speed:** on the unchanged 0.7 m step, the control reports the hard stop at tick 227 and subsequent stuck window, with no integrity flags. A separate injection restoring 9 m/s into the blocked face triggers both `reported_speed_unsupported` and `post_velocity_unsupported` through tick 319. Delivery and counted ordering stay valid. See `step-control/` and `step-restore-injection/`.
